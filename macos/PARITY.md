# SwiftUI replacement: feature parity and validation

The shipped application is the native SwiftUI app. Electron, Node, Go and libusb are not runtime requirements. Sparkle is the native signed-update framework. The comparison baseline is the user-owned fork at [`6eb3e7b`](https://github.com/aaditagrawal/openmtp/tree/6eb3e7b), before the SwiftUI replacement. Historical source links in this document intentionally remain pinned to that commit.

“Implemented” below describes source behavior and the named checks. It does not imply that a real phone, every supported macOS version, Finder dragging or accessibility navigation has been exercised. Remaining release checks are listed separately.

## Native integration contracts

`NativeFileIntegration.RemoteFile` contains a name, directory flag, connection/storage/object identity, optional byte count and a Sendable async materialization closure. The closure receives an owned staging directory and Progress; it must create the root item beneath that directory and return that exact URL. AppModel connects Progress cancellation to the tree transfer token and runs planning/execution through the same serialized MTPClient as browsing and queued copies.

Each request receives a fresh private staging directory with a hashed identity and random UUID. Old handles cannot return a previous phone's cached bytes. Exports into Finder's supplied target use a fully materialized sibling directory and an exclusive atomic rename, preserving an existing user file even if one appears during transfer. Cache pruning recognizes only the exact generated directory shape and never targets user destinations.

Apple API references: [NSFilePromiseProviderDelegate](https://developer.apple.com/documentation/appkit/nsfilepromiseproviderdelegate), [NSItemProvider](https://developer.apple.com/documentation/foundation/nsitemprovider), [QLPreviewPanelDataSource](https://developer.apple.com/documentation/quicklookui/qlpreviewpaneldatasource), [NSWorkspace file icons](https://developer.apple.com/documentation/appkit/nsworkspace/icon(for:)), [multi-item dragging sessions](https://developer.apple.com/documentation/appkit/nsview/begindraggingsession(with:event:source:)).

## Explicit behavior changes

- Finder natural ordering uses the full file name, including its extension, so `file2.txt` sorts before `file10.txt`. Legacy ordering lowercased the name and stripped file extensions. Folder-first grouping remains configurable.
- Matching does not globally lowercase remote paths. Exact remote names and destination filesystem case behavior determine conflicts, avoiding silent merging of two distinct case-sensitive phone entries. Unicode/case collisions that cannot be represented safely on the local filesystem fail preflight.
- Smart Sync on an MTP endpoint compares whole seconds. The historical helper also accepted numeric timestamps on both sides and preserved submillisecond differences; that local-to-local helper mode is not an MTP transfer path. Unknown native size or date metadata causes a copy rather than declaring an unverified match.
- Devices without filename-renaming support can receive new files and recursive folders. Skip, Keep Both and matching Smart Sync items remain available; replacing existing content requires safe rename support and otherwise fails before payload writes. An explicit unsupported-property response on a fresh staged file can retry only after exact-handle cleanup and source/destination revalidation. Access-denied or ambiguous transport failures never trigger that retry.
- Phone deletion is explicitly permanent and confirmed against captured items. Local deletion uses the Mac Trash. Conventional Mac shortcuts may differ from the legacy application's custom mappings.
- Signed native builds use Sparkle instead of electron-updater for automatic installation. Ad-hoc/developer builds retain manual installation because they have no production signing configuration. Stable native distribution requires a configured Developer ID signature, notarization and update-signing key; unsigned/ad-hoc prereleases must not be presented as notarized stable builds.

## Legacy preference migration

Legacy settings are a flat JSON object at `~/Library/Application Support/io.ganeshrvel.openmtp/settings.json`, or `$OPENMTP_PROFILE_DIR/settings.json` when overridden. Sources: [Storage.js](https://github.com/aaditagrawal/openmtp/blob/6eb3e7b/app/classes/Storage.js), [paths.js](https://github.com/aaditagrawal/openmtp/blob/6eb3e7b/app/constants/paths.js), [getAppDataPath](https://github.com/aaditagrawal/openmtp/blob/6eb3e7b/app/utils/files.js).

Compatible preferences are imported only when the corresponding native preference is absent: `appThemeMode`, `showLocalPane`, `showLocalPaneOnLeftSide`, `hideHiddenFiles.local/mtp` (invert), `fileExplorerListingType.local/mtp`, `showDirectoriesFirst`, `enableStatusBar`, `enableUsbHotplug`, `enableAutoUpdateCheck`, `enableBackgroundAutoUpdate` and `enablePrereleaseUpdates`. Import is read-only and must not rewrite the legacy JSON. Automatic installation preferences are effective on configured signed builds. Native preference migration and persistence tests are owned by the workspace implementation; check their final validation before claiming migration complete.

## Native update configuration

[Sparkle 2.10.1](https://github.com/sparkle-project/Sparkle/releases/tag/2.10.1) is pinned exactly in SwiftPM. Its [license](https://github.com/sparkle-project/Sparkle/blob/2.10.1/LICENSE) and bundled third-party notices must accompany distribution. Integration follows Sparkle's [programmatic setup](https://sparkle-project.org/documentation/programmatic-setup/) and [configuration](https://sparkle-project.org/documentation/customization/) APIs. It does not replace archives by running a downloaded shell script.

Packaging enables `OpenMTPAutomaticUpdatesEnabled` only with Developer ID signing, `SUPublicEDKey` and the owned `SUFeedURL`. The service accepts only `https://github.com/aaditagrawal/openmtp/releases/latest/download/appcast-<arm64|x86_64>.xml` for the matching CPU. An invalid/missing setup leaves the manual selector available. Archives are verified by Sparkle using the configured EdDSA public key; feed/archive signing is part of the release job, not a key generated by the application.

Stable clients use the stable feed and an empty allowed-channel set. Opted-in prerelease clients discover newer compatible native releases through the owned GitHub API, then use that release's exact `appcast-<CPU>.xml` asset. Discovery refreshes on startup, explicit check and once per day; transient discovery failures retain the last verified owned feed. Prerelease appcast items must use the `beta` channel. `sparkle:version` must match the monotonic numeric bundle build number; the human version can include the prerelease suffix. No downgrade is intentionally offered by the manual selector, and Sparkle handles version/OS selection for signed installation.

This repository contains no invented signing credentials. A complete automatic-install round trip cannot be validated without the user's configured release key/certificate and a signed published native release. That is a release-validation dependency, not evidence of automatic-install parity from a mock test.

## Validation and remaining release checks

Focused integration validation on 2026-11-05: all **20 tests in five suites** passed using Swift 6.4.2 on Quasar, macOS 27 arm64, targeting macOS 13. The actual Sparkle 2.10.1 binary dependency compiles with the service; configuration, channel and deferred-installation regression checks are included. File-provider tests exercise lazy export and actual incoming NSItemProvider callbacks for both files and folders. Tests ran from isolated staging `/Users/mav/Sandbox/openmtp-integrations-eLEwUa`; they did not modify a phone, terminate the existing app or overwrite the original source. The fixtures execute the protocol engine against a simulated device. The test runner's Testing.framework requires a newer runtime than the application's macOS 13 deployment target; this run does not establish macOS 13 runtime compatibility.
