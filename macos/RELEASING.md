# Native releases

GitHub Actions builds the Swift app for arm64 and x86_64 on macOS 26 runners. Each architecture passes native tests, strict Swift formatting, a release build, bundle verification, ZIP checksums and DMG verification. The workflows contain no Electron or JavaScript build steps.

`macos/VERSION` is the release SemVer. A release tag must equal `v` plus that value. The numeric CFBundleShortVersionString is its three-part core version; OpenMTPVersion preserves the complete prerelease version. CFBundleVersion uses the release workflow's increasing run number. Do not reset that workflow's build-number sequence after shipping Sparkle updates.

## Local artifacts

```sh
make test package
./macos/scripts/verify-package.sh
```

OPENMTP_ARCH defaults to the current CPU. Set it to arm64, x86_64 or universal to build explicitly. Signed auto-update releases use separate arm64 and x86_64 packages. Development output is ad-hoc signed. It is not notarized and uses manual downloads for updates.

The app keeps the existing bundle identity, io.ganeshrvel.openmtp, and includes the CLI and Sparkle framework. ZIP creation uses ditto to preserve framework symlinks. The DMG includes an Applications link. Artifacts are named `OpenMTP-<version>-macos-<architecture>.zip` and `.dmg`; per-architecture JSON records the minimum OS and signing state.

## Repository configuration

The release workflow accepts these existing-style repository secrets for Developer ID signing and notarization:

| Name | Value |
| --- | --- |
| CSC_LINK | Base64-encoded Developer ID Application PKCS#12, or an HTTPS download URL |
| CSC_KEY_PASSWORD | PKCS#12 password |
| APPLEID | Apple account used for notarization |
| APPLE_APP_SPECIFIC_PASSWORD | Its app-specific notarization password |
| APPLE_TEAM_ID | Developer team identifier |
| SPARKLE_PRIVATE_KEY | Sparkle Ed25519 private key exported by the pinned generate_keys tool |

Set the repository variable SPARKLE_PUBLIC_KEY to the matching base64 public key. Create/export keys with Sparkle's official generate_keys tool from `macos/.build/artifacts/sparkle/Sparkle/bin/`. Keep the private key outside the repository, in a secret manager. Never paste it into a pull request or command log.

The pipeline imports Developer ID into a temporary keychain, signs nested Sparkle helpers before the framework and app, notarizes and staples the app and DMG, then creates signed architecture-specific appcasts. Stable tags require all signing and update configuration. Ad-hoc prerelease tags can produce manual-install developer artifacts. No signing credentials are committed or generated by the workflow.

## Native updates

Sparkle 2.10.1 is pinned exactly in Package.swift and Package.resolved. SwiftPM verifies the upstream binary checksum. The app uses Sparkle only for Developer ID builds configured with a public key and owned feed URL. It requires signed feeds and signed archives before extraction. Update check and background installation preferences are separate; prereleases require explicit opt-in.

The stable feeds are:

- `https://github.com/aaditagrawal/openmtp/releases/latest/download/appcast-arm64.xml`
- `https://github.com/aaditagrawal/openmtp/releases/latest/download/appcast-x86_64.xml`

Each signed native release uploads both feeds. Beta clients discover the newest compatible owned release and use its exact architecture-specific feed; prerelease entries carry the beta channel. The strict release selector rejects old Electron artifacts, wrong CPU/minimum-OS packages, drafts and downgrades. Release assets carry the label `openmtp-native;minimum-macos=13.0`.

Release publication waits for both architecture jobs. It creates a draft, uploads all native packages/manifests/checksums/appcasts, then makes the release visible. There is no automatic publication from a pull request or master push. Tags initiate release builds; creating a tag is a separate release action.

## Validation limits

As of the replacement work, this repository has no configured Developer ID/notarization or Sparkle secrets. Local ad-hoc packaging and simulated update selection cannot establish a signed update round trip. Before a stable release, test an actual signed older-to-newer install, both CPU packages, physical-phone transfers and the user interactions recorded in VALIDATION.md.
